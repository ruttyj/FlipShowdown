Flip Showdown server map

How server/src is put together: the layers and the one-way rule between them, how the repositories sit over one SQLite file, the path a game action takes, and who creates, reads, updates and deletes each entity. The HTTP and WebSocket contract is in docs/backend-contract.md; the schema is in docs/database.md.

1 · Layers

Folders are grouped by role into six layers. A file may import its own layer and the ones below it, never above; eslint.config.js checks this with no-restricted-imports. Parts are classes that get their dependencies through the constructor; the providers build them and their parts (the Gemini client, model catalog and rate limit ScanService uses, the EntityGateway EntityService uses) and only they call app.get(). The one deliberate exception is the hold-to-vote and entry status trackers (managers/votes.js, managers/entryStatus.js), pure factory modules that VoteManager and EntryStatusManager wrap.

2 · Store and repositories

Production code reads and writes through the repositories, which DatabaseProvider hands out as repositories. One repository per table shares TableRepository; EntityGateway picks the repository for an entity name, so any name allowed by ENTITIES without a table of its own becomes a JSON row in records. The record-shaped store from openStore() is the tests' API; production uses it in only three places that tests patch or count (see docs/testing.md), so only buildRoomActionRunner, EntityService and createStoreViews are given the store.

3 · How a game action runs

Every game write, whether from a player, a passed vote or the stale-room sweep, goes through RoomActionRunner. It gives the action's handler a RoomUnitOfWork inside one database transaction and only tells the realtime hub once the transaction commits. Here is submit-score from a phone. A passed vote and the sweep call runAsSystem, which skips the access check.

4 · Tables and how they link

Unchanged by the restructure. Deleting a room cascades to its players, round scores and chat messages in SQLite itself, though the delete action removes them first so each sends an event.

5 · CRUD by entity

Who performs each operation: the class named is the one that decides to make the call. Game writes all happen inside a game action, on its RoomUnitOfWork (work), which writes through the repositories.

6 · Realtime managers

RealtimeHub builds the managers and the socket edge, and is the one object the rest of the server calls. Each manager owns one piece of live state and gets the others it needs through its constructor; the hub runs the steps that cross managers (after a publish, a membership change, a presence refresh or a liveness check). Every manager reads the same injected Clock.
